# Strict Review

Use Strict Review only when the current authorized mutation actually crosses a
permission or security boundary, creates an irreversible user-data effect,
migrates persistent data, or changes published compatibility or another public
contract. Keywords, importance, complexity, topic, and subjective risk do not
activate this method.

Freeze the stable candidate, crossed boundary, supplied acceptance criteria,
protected behavior, direct evidence, and any explicitly accepted fallback or
recovery condition. Examine the actual changed effect and the evidence needed
to show that it stays within authority and preserves the protected boundary.
Choose the order from the candidate rather than following a universal lens
sequence.

For every material finding, state the failed criterion, direct evidence,
effect, and smallest correction route. Missing required access or evidence
produces `BLOCKED`; a plausible but unobserved concern is not proof. Add an
independent Reviewer only for a separable bounded effect where independence
would change the gate, then synthesize under one Review owner.

Reviewer remains read-only. Return the supported verdict, unresolved findings,
residual uncertainty, and the exact evidence needed to close the gate without a
fixed report shape.
